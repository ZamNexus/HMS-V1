# Catalog modules: one shared reference-catalog base, ICD-10 as lookup-only

`MasterDataPage.tsx` is 867 lines managing 10 unrelated concerns behind one file/route: services, lab tests, banks, panels, wards/beds, guardian relations, ECG/ultrasound, diseases, expense categories, and clinic settings. Several of these are already slated to merge or change shape by earlier decisions — this ADR is where those land as concrete module boundaries.

**One base, several thin modules, not one merged table.** `ServiceCatalogModule` absorbs `ServicesTab` and `EcgUltrasoundTab` (per [ADR-0011](./0011-diagnostic-order-unification.md), `EcgUltrasoundTest` folds into `service_catalog`). `LabTestsTab`'s diagnostic-specific fields (`parameters[]`, `narrative` flag, `turnaroundHours`) become a `diagnostic_catalog_extension` table keyed 1:1 to a `service_catalog` row — the same base-entity-plus-extension shape already established for Doctor/User in [ADR-0010](./0010-doctor-separate-table-not-role-columns.md), reused here rather than inventing a second pattern for the same problem. `BankAccountsModule`, `PanelsModule`, and `GuardianRelationsModule` stay genuinely separate — a Panel is an insurance/corporate organization, not a billable service, and merging distinct domain concepts into one table just because their admin screens look similar would be the wrong kind of consolidation. `ExpenseCategoriesModule` gets the FK-with-fallback treatment from [ADR-0013](./0013-fk-with-fallback-normalization.md) too — `Expense.category` shadows a catalog exactly like the fields that ADR already covers, it just wasn't listed there. `ClinicSettingsTab` becomes its own tiny `TenantSettingsModule` — a singleton config row per tenant, not a list-shaped catalog, and forcing it into the catalog pattern would be a shape mismatch. `WardsTab`'s bed-management UI is superseded by the `BedAssignmentService` from the ward/bed candidate — not independently redesigned here, to avoid two candidates disagreeing about who owns bed state.

**Diseases/ICD-10 is not admin-CRUD at all.** [ADR-0014](./0014-icd10-and-diagnosis-cardinality.md) already decided diagnosis uses the full standard ICD-10 set, loaded once as static reference data — a real clinic doesn't "add a new disease," ICD-10 is an external maintained standard. `DiseasesTab`'s current create/edit UI has no real backend equivalent; the ICD-10 module exposes search/lookup only. This is a scope reduction, not a refactor target, and it's worth calling out explicitly because it's the one tab in `MasterDataPage` where "just refactor it like the others" would be the wrong move.

**The shared leverage point is `CatalogReferenceService`, not a shared table.** `ServiceCatalog`, `BankAccounts`, `Panels`, `GuardianRelations`, and `ExpenseCategories` all share the same interface shape (create/list/update/deactivate, plus the "entered outside the catalog, needs reconciliation" query from ADR-0013 — rows where the FK-with-fallback pattern's FK is null). One abstract base class implements that once; each catalog module is a thin adapter over it. This is where the actual depth lives — not in merging distinct domain concepts together, but in not reimplementing the same reconciliation query five times.

Rejected: one mega `CatalogModule` with one polymorphic table for everything — Panels, Banks, and GuardianRelations are distinct domain concepts with distinct fields and distinct consumers; collapsing them into one table trades real modeling clarity for a superficial resemblance (they all have a name and an active flag). Also rejected: treating ICD-10 like the other catalogs and building create/edit endpoints for it — contradicts ADR-0014's own reasoning (it's a standard, not clinic-curated data) and builds admin UI nobody will use.
