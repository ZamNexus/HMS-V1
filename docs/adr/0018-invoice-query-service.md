# InvoiceQueryService: one deep module for every revenue/balance read

The architecture review (candidate #5) found `billingAggregate.ts` already reused across 7+ call sites, but `DailySummaryReport.tsx` and `RevenueReport.tsx` bypass it and re-sum raw arrays directly — producing revenue figures missing services/imaging that actively disagree with the correct total. Deeper investigation surfaced more: neither report filters by date despite their names; `RevenueReport`'s trend chart and period comparison are entirely fabricated (a formula, not a query — `2000 + i * 400 + (i % 2) * 500`); `billingAggregate.ts` itself has a bug (`received` includes the full `imaging` total unconditionally, because `ImagingOrder` never had a `paymentStatus` field to filter by); and `RevenueReport`'s aging section omits lab/imaging/pharmacy balances entirely.

`InvoiceQueryService` (inside `BillingModule`, alongside the write-side `InvoiceService`) becomes the one legal read path for revenue and outstanding-balance figures, querying `invoice_lines` directly ([ADR-0009](./0009-unified-invoice-ledger.md)) rather than fanning out across five source tables the way `billingAggregate.ts` does today. This isn't a wrap of `billingAggregate.ts` — it supersedes it. Every line in the unified ledger already carries its own received/balance state, so the entire class of per-source-type bugs (the imaging-received miscalculation) can't recur: there's no `imaging`-vs-`imagingReceived` field pair to get wrong, because there's exactly one accounting of "received," for every line, regardless of source.

**Interface**: `revenueSummary(tenantId, locationId, dateRange, options?)` and `outstandingBalances(tenantId, locationId, asOfDate, options?)`, both mandatory on `dateRange`/`asOfDate` — no dateless call is possible, closing the "Daily Summary that ignores dates" bug structurally rather than by convention. Both return a breakdown by `source_type` (consultation/service/diagnostic/pharmacy).

**Revenue is reported net of tax and net of refunds, both shown separately, never folded into one number.** `grossRevenue` (line amounts, excluding Voided per [ADR-0016](./0016-archived-vs-voided.md)) minus `refundsAndCreditNotes` (the prototype's `ReceiptType: "Refund" | "Credit Note"`) gives `netRevenue`. `gstCollected` is broken out as its own figure, never counted as revenue — GST collected on a hospital's behalf is a liability owed to the tax authority, not clinic income; this is standard accounting practice, not a project-specific judgment call. Voided lines are excluded from every revenue figure by default but remain separately queryable via `options.includeVoided`, matching how real financial reconciliation treats voided transactions: visible, but not counted as earned.

**Seam and testability**: `InvoiceQueryService` queries its ORM directly — no injected repository port. Postgres is local-substitutable (a real stand-in exists — testcontainers or PGLite), not a remote service this system owns, so a port-and-adapter pair here would be indirection with only one real adapter behind it. Tests run the service's actual methods against a seeded local Postgres stand-in and assert on returned results, exercising real query behavior rather than a hand-maintained fake's approximation of it. All aggregation math (gross/net/GST-split/voided-exclusion/source-type grouping) still lives in `InvoiceQueryService` itself — that's what stays pure and testable, independent of how the data got there.

**Explicitly deferred, not silently dropped**: real time-series revenue (day-by-day trend, period-over-period comparison) and payer-mix breakdown (self-pay vs. panel vs. insurance) are not part of this interface — both are 100% fabricated placeholder data in the prototype today, and real versions need date-bucketed grouping, a materially bigger interface than point-in-time totals. `invoice_lines` already carries what a future version needs (payment mode; patient→panel is joinable), so nothing is lost by deferring. Doctor/panel commission net-of-share reporting is deferred for the same reason as [ADR-0007](./0007-commission-rate-snapshot-not-full-payout-ledger.md): the rate snapshot exists on each line; the reporting layer on top of it doesn't need to exist yet.

Rejected: incrementally patching `billingAggregate.ts` to add services/imaging to the two broken reports — preserves the fan-out shape that caused the bug, and leaves a second, parallel aggregation path alive alongside the new one instead of one canonical read path. Also rejected: a separate top-level `ReportingModule` — the query logic is intimately coupled to the ledger's own shape either way; a separate module here would just re-export `BillingModule`'s internals, failing the deletion test.
