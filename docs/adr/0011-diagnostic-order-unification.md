# Diagnostic Order unification: one request record for Lab and Imaging

The prototype already treats Lab and Imaging tests as one underlying catalog — `LAB_TESTS` includes categories `Radiology` and `Cardiology` alongside `Haematology`/`Biochemistry`/`Serology`/`Urine Analysis`, and `ImagingOrderFormPage` builds its entire test picker by filtering that same `LAB_TESTS` array (`category === "Radiology" || category === "Cardiology"`) rather than drawing from a separate catalog. Both `LabOrder` and `ImagingOrder` reuse the exact same `LabOrderTest` line shape, which already carries both `results?: LabResultParam[]` (numeric per-parameter results) and `narrativeResult?: string` (free text) on one struct — the "unified result shape" already exists at the line level. What's actually split, and inconsistently, is the *order header*: `LabOrder` carries `sampleType`/`sampleId`/`collectedBy`/`clinicalNotes`/`paymentStatus`/`pathologistRemarks`/`performedBy`/`verifiedBy`; `ImagingOrder` has none of them, despite both being "order a test, get a result, bill for it."

We're replacing `LabOrder`/`ImagingOrder` with one `diagnostic_order` table, `type: lab | imaging`. The lab-only header fields (sample handling, pathologist remarks) become nullable, populated only when `type = lab`. ECG/Ultrasound continue to route through `type = imaging`. The discriminator is based on how the result is produced and reported — a specimen analyzed into numeric parameters is `lab`; a procedure performed on the patient producing a narrative/trace report is `imaging` — not on whether the test literally produces a picture. Under this definition there's no genuinely ambiguous test: a ward point-of-care blood gas panel is structurally `lab` (numeric parameters from a blood specimen) regardless of where it's physically run. Where/how a test is performed (central lab vs. bedside) is a separate `performed_at` attribute on the order, not a third discriminator value.

`diagnostic_order` stays the request header only. Each ordered test is a `diagnostic_order_line` — the table that actually replaces the embedded `LabOrderTest[]` array — referencing a `service_catalog` item and snapshotting its rate/discount/gst at order time, the same snapshot pattern already used for `LabOrderTest.charges`/`testName` and for commission rates ([ADR-0007](./0007-commission-rate-snapshot-not-full-payout-ledger.md)). Results stay at the line level too, inheriting the prototype's existing split unchanged: a child `diagnostic_result_parameter` table for numeric multi-parameter results, or a `narrative_result` text field directly on the line — selected by the catalog item's `narrative` flag, exactly as `LabTest.narrative` already does.

**Catalog vs. order line vs. invoice line — three records, not two.** `EcgUltrasoundTest` folds into the general `service_catalog` for billing, continuing a direction the prototype already started (`SERVICE_CATALOG` is `LAB_TESTS` mapped into `ServiceCatalogItem` shape, concatenated with `EXTRA_SERVICES`). This gives three distinct, connected records: the **catalog item** (what can be ordered, and its current price/category/result-shape), the **`diagnostic_order_line`** (what was actually ordered on this order, rate/discount snapshotted), and the **`invoice_line`** ([ADR-0009](./0009-unified-invoice-ledger.md), `source_type = 'diagnostic'`). Because the prototype already prices and discounts per-test rather than per-order, an `invoice_line`'s source reference is the `diagnostic_order_line`, not the parent `diagnostic_order` — this preserves billing granularity that already exists rather than inventing new behavior.

Rejected: keeping `LabOrder`/`ImagingOrder` as two tables and just fixing the field asymmetry — this preserves a lab-vs-imaging *order* distinction that the catalog and result model never actually had, forcing every cross-cutting report (turnaround time, revenue by diagnostic category) to union two tables instead of filtering one. Also rejected: a three-way discriminator (`lab | imaging | point_of_care`) for bedside tests like blood gas panels — conflates *where* a test is performed with *what kind* of result it produces; `performed_at` is the right place for that distinction.
